Campo Minado parece simples à primeira vista — é um grid com números e minas. Mas implementá-lo do zero revela várias decisões técnicas interessantes: como distribuir minas de forma verdadeiramente aleatória? Como garantir que o primeiro clique nunca seja uma mina? Como implementar o reveal em cascata de células vazias sem travar a UI? Neste artigo mostro como resolvi cada uma dessas questões no Campo Minado Evolution.

Atualizado em 22 de outubro de 2026: o artigo foi revisado para refletir a implementação atual do app — células imutáveis, sorteio de minas com lista embaralhada e flood fill iterativo com fila.

A estrutura de dados: modelando uma célula

Cada posição do tabuleiro é representada por um objeto Cell imutável, com todo o estado necessário para renderização e lógica do jogo: 

class Cell {
  final int row;
  final int col;
  final bool isMine;
  final bool isRevealed;
  final bool isFlagged;
  final int adjacentMines;
  final bool isExploded;

  const Cell({
    required this.row,
    required this.col,
    required this.isMine,
    required this.isRevealed,
    required this.isFlagged,
    required this.adjacentMines,
    this.isExploded = false,
  });

  Cell copyWith({
    bool? isMine,
    bool? isRevealed,
    bool? isFlagged,
    int? adjacentMines,
    bool? isExploded,
  }) {
    return Cell(
      row: row,
      col: col,
      isMine: isMine ?? this.isMine,
      isRevealed: isRevealed ?? this.isRevealed,
      isFlagged: isFlagged ?? this.isFlagged,
      adjacentMines: adjacentMines ?? this.adjacentMines,
      isExploded: isExploded ?? this.isExploded,
    );
  }
}

Todos os campos são final: qualquer mudança gera uma nova célula via copyWith. Isso evita efeitos colaterais escondidos e permite que o Riverpod compare o estado antigo com o novo para saber exatamente o que mudou.

O tabuleiro inteiro é uma lista bidimensional inicializada com células limpas. Nenhuma mina é colocada na criação — esse tabuleiro inicial é só um espaço reservado, e as minas são sorteadas no primeiro toque, como veremos em seguida. 

List<List<Cell>> createEmptyBoard(int rows, int cols) {
  return List.generate(
    rows,
    (r) => List.generate(
      cols,
      (c) => Cell(
        row: r,
        col: c,
        isMine: false,
        isRevealed: false,
        isFlagged: false,
        adjacentMines: 0,
      ),
    ),
  );
}

Distribuindo as minas: o problema do primeiro clique

Uma regra clássica do Campo Minado: o primeiro clique nunca pode explodir uma mina. Isso significa que as minas precisam ser distribuídas após o primeiro clique, excluindo a célula tocada e todos os seus vizinhos do sorteio. No app, o primeiro toque regenera o tabuleiro passando a posição tocada como zona segura: 

void placeMines(
  List<List<Cell>> board,
  int count, {
  int? safeRow,
  int? safeCol,
}) {
  final rows = board.length;
  final cols = board[0].length;

  final excluded = <(int, int)>{};
  if (safeRow != null && safeCol != null) {
    for (final dr in [-1, 0, 1]) {
      for (final dc in [-1, 0, 1]) {
        excluded.add((safeRow + dr, safeCol + dc));
      }
    }
  }

  final positions = [
    for (int r = 0; r < rows; r++)
      for (int c = 0; c < cols; c++)
        if (!excluded.contains((r, c))) (r, c),
  ];

  positions.shuffle(Random());

  for (int i = 0; i < count; i++) {
    final (r, c) = positions[i];
    board[r][c] = board[r][c].copyWith(isMine: true);
  }
}

Em vez de sortear coordenadas aleatórias e descartar as repetidas até completar o total de minas, monto a lista de posições candidatas (tudo fora da zona segura), embaralho e pego as primeiras count. O custo é previsível, sem nenhum loop que possa girar indefinidamente, e a distribuição continua uniforme. A zona de exclusão de 3×3 garante que o primeiro toque abra um espaço para o jogador raciocinar. Se o número de minas exceder as posições disponíveis, o use case lança uma exceção em vez de gerar um tabuleiro inválido (o código acima é uma versão simplificada).

Calculando os números adjacentes

Após distribuir as minas, percorremos todo o tabuleiro e calculamos quantas minas existem nos 8 vizinhos de cada célula que não é mina: 

void calculateAdjacentCounts(List<List<Cell>> board) {
  final rows = board.length;
  final cols = board[0].length;
  const offsets = [-1, 0, 1];

  for (int r = 0; r < rows; r++) {
    for (int c = 0; c < cols; c++) {
      if (board[r][c].isMine) continue;

      int count = 0;
      for (final dr in offsets) {
        for (final dc in offsets) {
          if (dr == 0 && dc == 0) continue;
          final nr = r + dr;
          final nc = c + dc;
          if (nr >= 0 && nr < rows && nc >= 0 && nc < cols &&
              board[nr][nc].isMine) {
            count++;
          }
        }
      }
      board[r][c] = board[r][c].copyWith(adjacentMines: count);
    }
  }
}

O reveal em cascata: flood fill iterativo com fila

Quando o jogador toca em uma célula com adjacentMines == 0, todas as células vazias conectadas devem ser reveladas automaticamente — e os números nas bordas dessa região também. Isso é um algoritmo de flood fill (preenchimento por inundação), o mesmo usado em ferramentas de pintura tipo balde. 

List<List<Cell>> reveal(List<List<Cell>> board, int row, int col) {
  final updated = board.map((r) => [...r]).toList();
  final pending = Queue<(int, int)>()..add((row, col));

  while (pending.isNotEmpty) {
    final (r, c) = pending.removeFirst();
    final cell = updated[r][c];
    if (cell.isRevealed || cell.isFlagged) continue;

    updated[r][c] = cell.copyWith(isRevealed: true);

    if (cell.adjacentMines == 0 && !cell.isMine) {
      for (final neighbor in neighborsOf(updated, r, c)) {
        pending.add((neighbor.row, neighbor.col));
      }
    }
  }
  return updated;
}

A versão recursiva é a mais direta de escrever, mas a pilha de chamadas cresce com o tamanho da região vazia — e em tabuleiros grandes isso é um risco. Por isso o reveal usa uma fila (Queue): cada célula vazia empilha seus vizinhos para processar depois, e o laço termina quando a fila esvazia. Células já reveladas ou marcadas com bandeira são ignoradas, e as células com número maior que zero são reveladas mas não expandem a busca (as bordas da região). O reveal trabalha sobre uma cópia do tabuleiro, preservando a imutabilidade do estado. O auxiliar neighborsOf devolve as até 8 células vizinhas que estão dentro dos limites do tabuleiro.

Renderizando o tabuleiro com Flutter

O tabuleiro é renderizado com GridView.builder com um delegate de contagem fixa de colunas. O tamanho da célula é calculado a partir do espaço disponível, para que o grid preencha a tela em qualquer aparelho. Cada célula é um ConsumerWidget que observa apenas a sua posição no estado: 

class CellWidget extends ConsumerWidget {
  // ...
  @override
  Widget build(BuildContext context, WidgetRef ref) {
    final cell = ref.watch(
      gameProvider.select((s) => s.game.board[row][col]),
    );

    return GestureDetector(
      onTap: () => _onTap(ref),
      onLongPress: () => _onLongPress(ref),
      child: CellContentWidget(cell: cell, cellSize: cellSize),
    );
  }
}

Como o select compara a Cell antiga com a nova, apenas as células que mudaram são reconstruídas — fundamental no modo Difícil, com centenas de células. O toque simples revela a célula; o toque longo coloca a bandeira. Há também um botão de modo bandeira, que faz o toque simples marcar em vez de revelar, para quem prefere não usar o toque longo. 

GridView.builder(
  physics: const NeverScrollableScrollPhysics(),
  gridDelegate: SliverGridDelegateWithFixedCrossAxisCount(
    crossAxisCount: cols,
    childAspectRatio: 1.0,
    mainAxisSpacing: spacing,
    crossAxisSpacing: spacing,
  ),
  itemCount: rows * cols,
  itemBuilder: (context, index) {
    final row = index ~/ cols;
    final col = index % cols;
    return CellWidget(
      key: ValueKey('cell_${row}_$col'),
      row: row,
      col: col,
      cellSize: cellSize,
    );

)

O CellContentWidget decide o que exibir: célula coberta, bandeira, número colorido ou mina. As cores dos números seguem a convenção clássica do Campo Minado: 1 azul, 2 verde, 3 vermelho, etc.

Condições de vitória e derrota

As duas condições são verificadas após cada jogada. A derrota acontece quando a célula revelada é uma mina; a vitória, quando não resta nenhuma célula sem mina coberta:

bool checkVictory(List<List<Cell>> board) {
  return board
      .expand((row) => row)
      .where((cell) => !cell.isRevealed && !cell.isMine)
      .isEmpty;
}

Na vitória, o cronômetro para, o app toca o som de vitória, vibra e salva o tempo nas estatísticas (Drift/SQLite), que alimentam o melhor tempo e a taxa de vitória por dificuldade. Na derrota, todas as minas são reveladas, a que explodiu é marcada com isExploded: true para receber a animação própria, e a derrota também é registrada.

Implementar Campo Minado em Flutter é um exercício excelente porque combina algoritmos clássicos (flood fill, geração aleatória com restrição) com UI reativa. Toda a lógica vive fora da árvore de widgets, em use cases puros — GenerateBoardUseCase, RevealCellUseCase, CheckVictoryUseCase e ToggleFlagUseCase — orquestrados por um GameViewModel (Notifier do Riverpod). Como são funções sobre estado imutável, são simples de testar sem mocks, e a UI só reconstrói o que mudou.

Minesweeper looks simple at first glance — it's a grid of numbers and mines. But implementing it from scratch reveals several interesting technical decisions: how do you distribute mines in a truly random way? How do you guarantee the first click is never a mine? How do you implement the cascading reveal of empty cells without freezing the UI? In this article I show how I solved each of these questions in Campo Minado Evolution.

Each board position is represented by an immutable Cell object holding all the state needed for rendering and game logic:

Distributing the mines: the first-click problem

A classic Minesweeper rule: the first click can never explode a mine. That means mines need to be distributed after the first click, excluding the tapped cell and all of its neighbors from the draw. In the app, the first tap regenerates the board, passing the tapped position as the safe zone: 

void placeMines(
  List<List<Cell>> board,
  int count, {
  int? safeRow,
  int? safeCol,
}) {
  final rows = board.length;
  final cols = board[0].length;

  final excluded = <(int, int)>{};
  if (safeRow != null && safeCol != null) {
    for (final dr in [-1, 0, 1]) {
      for (final dc in [-1, 0, 1]) {
        excluded.add((safeRow + dr, safeCol + dc));
      }
    }
  }

  final positions = [
    for (int r = 0; r < rows; r++)
      for (int c = 0; c < cols; c++)
        if (!excluded.contains((r, c))) (r, c),
  ];

  positions.shuffle(Random());

  for (int i = 0; i < count; i++) {
    final (r, c) = positions[i];
    board[r][c] = board[r][c].copyWith(isMine: true);
  }
}

Instead of drawing random coordinates and discarding duplicates until the mine total is reached, I build the list of candidate positions (everything outside the safe zone), shuffle it, and take the first count. The cost is predictable, there is no loop that could spin indefinitely, and the distribution stays uniform. The 3×3 exclusion zone guarantees the first tap opens up some room for the player to reason. If the number of mines exceeds the available positions, the use case throws instead of producing an invalid board (the code above is a simplified version).

The cascading reveal: iterative flood fill with a queue

When the player taps a cell with adjacentMines == 0, every connected empty cell must be revealed automatically — along with the numbers at the edges of that region. This is a flood fill algorithm, the same technique used by bucket-fill tools in paint programs. 

List<List<Cell>> reveal(List<List<Cell>> board, int row, int col) {
  final updated = board.map((r) => [...r]).toList();
  final pending = Queue<(int, int)>()..add((row, col));

  while (pending.isNotEmpty) {
    final (r, c) = pending.removeFirst();
    final cell = updated[r][c];
    if (cell.isRevealed || cell.isFlagged) continue;

    updated[r][c] = cell.copyWith(isRevealed: true);

    if (cell.adjacentMines == 0 && !cell.isMine) {
      for (final neighbor in neighborsOf(updated, r, c)) {
        pending.add((neighbor.row, neighbor.col));
      }
    }
  }
  return updated;
}

The recursive version is the simplest to write, but the call stack grows with the size of the empty region — which is a risk on large boards. That's why the reveal uses a queue (Queue): each empty cell enqueues its neighbors to process later, and the loop ends when the queue is empty. Cells that are already revealed or flagged are skipped, and cells with a number greater than zero are revealed but don't expand the search (the edges of the region). The reveal works on a copy of the board, preserving the immutability of the state. The neighborsOf helper returns the up-to-8 neighboring cells that fall within the board bounds.

Win and loss conditions

Both conditions are checked after every move. A loss happens when the revealed cell is a mine; a win, when no covered non-mine cell remains:

bool checkVictory(List<List<Cell>> board) {
  return board
      .expand((row) => row)
      .where((cell) => !cell.isRevealed && !cell.isMine)
      .isEmpty;
}

On a win, the timer stops, the app plays the victory sound, vibrates, and saves the time to the stats (Drift/SQLite), which feed the best time and win rate per difficulty. On a loss, every mine is revealed, the one that exploded is marked with isExploded: true so it gets its own animation, and the defeat is recorded too.

All the logic lives outside the widget tree, in pure use cases — GenerateBoardUseCase, RevealCellUseCase, CheckVictoryUseCase, and ToggleFlagUseCase — orchestrated by a GameViewModel (a Riverpod Notifier). Since they are functions over immutable state, they're simple to test without mocks, and the UI only rebuilds what changed.

}

El revelado en cascada: flood fill iterativo con cola

Cuando el jugador toca una celda con adjacentMines == 0, todas las celdas vacías conectadas deben revelarse automáticamente — junto con los números en los bordes de esa región. Este es un algoritmo de flood fill (relleno por inundación), el mismo que usan las herramientas de relleno tipo balde en programas de pintura. 

List<List<Cell>> reveal(List<List<Cell>> board, int row, int col) {
  final updated = board.map((r) => [...r]).toList();
  final pending = Queue<(int, int)>()..add((row, col));

  while (pending.isNotEmpty) {
    final (r, c) = pending.removeFirst();
    final cell = updated[r][c];
    if (cell.isRevealed || cell.isFlagged) continue;

    updated[r][c] = cell.copyWith(isRevealed: true);

    if (cell.adjacentMines == 0 && !cell.isMine) {
      for (final neighbor in neighborsOf(updated, r, c)) {
        pending.add((neighbor.row, neighbor.col));
      }
    }
  }
  return updated;
}

La versión recursiva es la más directa de escribir, pero la pila de llamadas crece con el tamaño de la región vacía — y en tableros grandes eso es un riesgo. Por eso el revelado usa una cola (Queue): cada celda vacía encola a sus vecinas para procesarlas después, y el bucle termina cuando la cola se vacía. Las celdas ya reveladas o marcadas con bandera se omiten, y las celdas con un número mayor que cero se revelan pero no expanden la búsqueda (los bordes de la región). El revelado trabaja sobre una copia del tablero, preservando la inmutabilidad del estado. El auxiliar neighborsOf devuelve las hasta 8 celdas vecinas que están dentro de los límites del tablero.

Renderizando el tablero con Flutter

El tablero se renderiza con GridView.builder usando un delegate de conteo fijo de columnas. El tamaño de la celda se calcula a partir del espacio disponible, para que la cuadrícula llene la pantalla en cualquier dispositivo. Cada celda es un ConsumerWidget que observa solo su posición en el estado: 

class CellWidget extends ConsumerWidget {
  // ...
  @override
  Widget build(BuildContext context, WidgetRef ref) {
    final cell = ref.watch(
      gameProvider.select((s) => s.game.board[row][col]),
    );

    return GestureDetector(
      onTap: () => _onTap(ref),
      onLongPress: () => _onLongPress(ref),
      child: CellContentWidget(cell: cell, cellSize: cellSize),
    );
  }
}

Como select compara la Cell anterior con la nueva, solo se reconstruyen las celdas que cambiaron — fundamental en el modo Difícil, con cientos de celdas. El toque simple revela la celda; la pulsación larga coloca la bandera. También hay un botón de modo bandera, que hace que el toque simple marque en lugar de revelar, para quien prefiere no usar la pulsación larga. 

GridView.builder(
  physics: const NeverScrollableScrollPhysics(),
  gridDelegate: SliverGridDelegateWithFixedCrossAxisCount(
    crossAxisCount: cols,
    childAspectRatio: 1.0,
    mainAxisSpacing: spacing,
    crossAxisSpacing: spacing,
  ),
  itemCount: rows * cols,
  itemBuilder: (context, index) {
    final row = index ~/ cols;
    final col = index % cols;
    return CellWidget(
      key: ValueKey('cell_${row}_$col'),
      row: row,
      col: col,
      cellSize: cellSize,
    );
  },
)

El CellContentWidget decide qué mostrar: celda cubierta, bandera, número coloreado o mina. Los colores de los números siguen la convención clásica del Buscaminas: 1 azul, 2 verde, 3 rojo, etc.

Condiciones de victoria y derrota

Ambas condiciones se verifican después de cada jugada. La derrota ocurre cuando la celda revelada es una mina; la victoria, cuando no queda ninguna celda sin mina cubierta:

bool checkVictory(List<List<Cell>> board) {
  return board
      .expand((row) => row)
      .where((cell) => !cell.isRevealed && !cell.isMine)
      .isEmpty;
}

En la victoria, el cronómetro se detiene, la app reproduce el sonido de victoria, vibra y guarda el tiempo en las estadísticas (Drift/SQLite), que alimentan el mejor tiempo y la tasa de victoria por dificultad. En la derrota, todas las minas se revelan, la que explotó se marca con isExploded: true para recibir su propia animación, y la derrota también se registra.

Implementar el Buscaminas en Flutter es un ejercicio excelente porque combina algoritmos clásicos (flood fill, generación aleatoria con restricciones) con UI reactiva. Toda la lógica vive fuera del árbol de widgets, en use cases puros — GenerateBoardUseCase, RevealCellUseCase, CheckVictoryUseCase y ToggleFlagUseCase — orquestados por un GameViewModel (un Notifier de Riverpod). Al ser funciones sobre estado inmutable, son simples de probar sin mocks, y la UI solo reconstruye lo que cambió.
